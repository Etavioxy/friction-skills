# Issue 生命周期

## 何时记录

触发条件：

1. **上游项目**：发现了依赖项目的设计缺陷或结构性缺失时，需要记录情况和具体缺失内容。
2. **Agent 约束**：agent 基于项目设计进行探索，用户指出 agent 的回答/行为存在问题时，需要记录agent表现和约束缺陷、盲点。
3. **用户使用过程**：用户指出了软件不符合预期时，需要记录现象和用户需求。

提交后 review 发现的实际 bug 也可登记。issue 必须用户确认后再落笔，不自行判断。

## 载体

项目根目录 `issues.md`。如果还不存在则创建。

## 条目格式

### Issue 条目

每条 issue 全局递增编号（从 1 开始）。标题行 = 编号 + 描述 + 状态：

```
## #N 一句话描述问题 (YYYY-MM-DD) — open

一段话描述症状、影响、建议。可以使用概念解释但不能包含大量代码细节变量。

可选：依次增补一句话描述。
```

问题正文一段话讲清楚：症状、影响、建议。不需要单独的"严重程度""触发场景""说明"字段——这些都融进描述里。

规则：
- N 全局递增（跨整个文件，不因场景分组而重置），不因删除/排序而重新编号
- 需要检查 branch / worktree 登记，搜索现有 `*issue*` 分支，取最大编号加一作为建议编号；若出现多个分支重复编号，合并进入主路径后，应该用 `N-a, N-b, ...` 区分
- 状态在标题末尾：`— open` / `— fixed`
- 同一编号只出现一次
- 描述直接写，不套模板字段

增补描述：
- 禁止删除原描述。
- reopen时增补 issue 描述和打回原因。
- 关闭时增补 issue 原因和修复方法。
- 增补后立刻补 issues.md 的提交。

### 场景描述节

当一个场景产生多个问题时，用场景描述来划分，先写日期块下，先写一段场景描述——交代这次问题的上下文。然后再列出这一批 issue。

```
***

**触发场景**: 用户做了什么。

**表现**: 发生了什么。
```

## 登记即提交

issues.md 每次变更（新增、补充描述、关 issue）必须立即单独 commit，不等修复完成。

## 提交格式

涉及 issue 的 commit 必须标注编号（方括号）：

```
docs: (issues) [#N] 登记/更新问题     # 登记或更新描述
fix: (<modules>) [#N] 简述修了什么       # 修复
```

关联方向是单向的 **commit → issue**：issue 只登记问题本身，不记修复 commit（commit 会因 rebase/amend 变化）。

## 关闭条件

修复完成后、提交前，用 agent 严格 review 待提交的 diff，需结合 issue 文件，确认变更正确、无可改进的点、测试过程完善。

agent review 通过后，重新确认 Issue、草稿、修复变更与验证证据一致。

确认一致后先提交修复，然后增补 issue 原因和修复方法，进行 issue 提交：commit 引用编号 + 标题状态改为 `— fixed`。
